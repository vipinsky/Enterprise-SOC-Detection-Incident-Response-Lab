# Detection 008 — DNS & Network Connection Hunting

A Wazuh and Sysmon threat-hunting lab that collects Windows DNS-query and network-connection telemetry and flags queries to selected suspicious-looking domains for analyst review.

## Executive Summary
The Wazuh dashboard search was configured for:
`rule.id:(100600 OR 100601 OR 100602 OR 100603 OR 100604 OR 100605 OR 100610 OR 100611 OR 100612 OR 100613 OR 100400)`

The dashboard displayed **395 alert hits** in the selected last-week range and **0 alerts at Level 12 or above**. The visible results are mostly Level 3 Sysmon network connection and DNS-query events. Two custom Level 10 alerts were supplied for DNS queries to:
- `suspicious-test-domain.xyz`
- `another-test.top`

Both were generated by rule `100604`, mapped to MITRE ATT&CK `T1568 — Dynamic Resolution`. These events demonstrate that the custom rule fired; they do **not** prove C2 communication or malware infection.

## Important Findings
- Rule `100604` fired on `suspicious-test-domain.xyz` and `another-test.top` at approximately **18:15:31 UTC+05:30** according to the indexed Wazuh alert timestamp.
- The supplied Sysmon process fields associate both queries with `powershell.exe` (PID `1696`) running as `DESKTOP-0P32A1N\vipin`.
- Both events have `queryStatus` `9003`; the accompanying query-result fields show nameserver records. Verify the resolver and raw Windows event before concluding what the status indicates.
- Other DNS events show expected-looking software activity for OneDrive and Microsoft services, plus `example.com`, `microsoft.com`, `wpad`, `localdomain`, and the local computer name.
- The `example.com` query came from `powershell.exe` (PID `1696`) and returned addresses in the Sysmon event data.
- Screenshots and records show endpoint IP `.148` in earlier events and `.152` in later events. Confirm whether this reflects DHCP/IP change or a lab addressing update.
- Sysmon's embedded `UtcTime` values do not consistently match `systemTime`/Wazuh timestamps in the supplied records. Time correlation should be validated before writing a precise sequence.

## Analyst Verdict
**DNS/network monitoring detections validated; possible suspicious DNS activity requires contextual review; C2 not confirmed.**

The custom rule detected two DNS lookups to test-like, uncommon-TLD domains from PowerShell. This is useful for a threat-hunting lab, but a DNS lookup alone does not establish a successful connection, command-and-control session, or compromise. The dashboard contains a large volume of lower-level telemetry, so triage should prioritize the Level 10 custom detections and correlate them with process, network, and DNS records.

## MITRE ATT&CK
- `T1568 — Dynamic Resolution` (the mapping on rule `100604`).
- Rule `100600` and `100400` are telemetry collection rules in the supplied evidence; no additional ATT&CK mapping was shown for those records.

## Investigation Checklist
1. Confirm the two test-domain lookups were deliberately generated as part of the lab.
2. Correlate each DNS query with Sysmon Event ID 22, process creation Event ID 1, network connection Event ID 3, and any firewall/proxy logs available.
3. Check whether a connection followed the DNS query; do not treat DNS resolution as proof of a C2 session.
4. Verify the executable path and process ancestry of `powershell.exe` (PID `1696`) and review the command line from Event ID 1.
5. Compare the domains with trusted threat-intelligence sources before assigning reputation or maliciousness.
6. Validate why `window10` appears with both `.148` and `.152`; check DHCP/IP assignment and agent metadata.
7. Reconcile event time fields (`eventdata.utcTime`, `systemTime`, and Wazuh timestamp) before generating an exact timeline.
8. Review the custom XML for `100604`; the exact match conditions and thresholds were not supplied.
9. Tune routine Microsoft/OneDrive and local discovery queries separately from suspicious-domain matches to reduce noise.
