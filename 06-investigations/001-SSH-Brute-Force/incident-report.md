# IR-001 — SSH Brute Force Investigation

## 1. Executive Summary

**Incident ID:** IR-001  
**Incident Type:** SSH Authentication Attack Investigation  
**Severity:** High — provisional, pending authorization and post-login investigation  
**Status:** Investigating  
**Detection Platform:** Wazuh  
**Affected Asset:** `ubuntu_vm2` — `192.168.34.143`  
**Investigation Date:** October 17, 2026 (UTC+05:30)  
**Analyst:** Vipin Kumar

### Summary

Wazuh generated a Level 10 security alert indicating multiple SSH authentication failures originating from `192.168.34.138` and targeting the Ubuntu endpoint `ubuntu_vm2` (`192.168.34.143`). The alert was generated by custom Wazuh rule `100200`, titled "Multiple SSH authentication failures from same source - possible brute force."

The Wazuh event contains four preceding failed SSH authentication records between `11:56:00` and `11:56:08` on October 17, 2026. The endpoint's authentication log subsequently records additional failures, including events at approximately `12:10:51` through `12:11:07`.

At `12:11:35.546310` (UTC+05:30), the endpoint recorded a successful password-based SSH login for user `vm2` from the same source IP, `192.168.34.138`. At `12:12:09`, a sudo session was opened by `vm2` to execute `/usr/bin/tail -n 50 /var/log/auth.log`.

The sequence of repeated authentication failures followed by a successful login from the same source is suspicious and warrants immediate investigation. However, the available evidence does not establish whether the source was an authorized administrator, whether the correct password was eventually entered legitimately, or whether an attacker obtained unauthorized access.

**Recommended action:** Validate whether the source IP and successful login were authorized, investigate commands and processes executed during the SSH session, review subsequent authentication activity, and preserve relevant logs. Escalate if the login cannot be explained by an authorized lab activity.

## 2. Objective

Investigate repeated SSH authentication failures against the Ubuntu endpoint, determine whether the activity is consistent with brute-force behavior, establish whether authentication subsequently succeeded, examine related post-login activity, and recommend appropriate containment and remediation actions.

The investigation aims to:

- Validate the Wazuh detection and its triggering conditions.
- Identify the source IP and targeted account.
- Reconstruct the authentication timeline.
- Determine whether a successful login followed the failures.
- Investigate the subsequent sudo activity.
- Assess whether the available evidence supports unauthorized access.
- Document findings, detection limitations, and recommended response actions.

## 5. Detection Logic

### Rule 100200 — SSH Brute Force

The custom rule is designed to identify repeated SSH authentication failures originating from the same source IP.

The relevant configuration is:

- `<if_matched_sid>5760</if_matched_sid>`: Uses previously matched events associated with the specified base rule.
- `<same_source_ip />`: Correlates events by source IP.
- `frequency="5"`: Configures the required event frequency.
- `timeframe="180"`: Defines the correlation window in seconds.
- `ignore="180"`: Configures an alert-suppression period.
- `level="10"`: Assigns a high-priority alert level.

The detection uses SSH authentication events collected from `/var/log/auth.log`.

### Detection outcome

Wazuh generated the expected Level 10 custom alert for repeated SSH authentication failures from `192.168.34.138`.

However, the rule must be tested against controlled samples to establish whether its threshold, event matching, and suppression behavior operate exactly as intended.

### Related Rule 100201 — Successful Login After Brute Force

The second rule is intended to detect successful SSH authentication following a brute-force alert within a five-minute window.

The available logs show a successful login at `12:11:35.546310`, but the supplied evidence does not include an alert generated by rule `100201`.

Therefore, the successful-login correlation rule's operational effectiveness remains unverified.

### Detection limitations

- The supplied Wazuh alert occurred around 11:56, while the successful login occurred around 12:11. These events are approximately 15 minutes apart and cannot be assumed to belong to the same five-minute correlation window.
- Additional failures occurred shortly before the successful login, but the corresponding Wazuh alerts and correlation state have not been supplied.
- The exact behavior of the rule's `ignore` setting and the rule's event correlation should be verified.
- A successful login after repeated failures does not, on its own, prove that an attacker compromised an account.

## 6. Investigation Questions

### 1. How many failed login attempts occurred?

The initial alert contains five visible failed-password records, including the triggering event.

The supplied authentication log contains at least nine explicit `Failed password` records across the two observed periods:

- Initial period: `11:56:00` to `11:56:15`
- Later period: `12:10:51` to `12:11:07`

Additional PAM authentication failure messages are also present. These should not automatically be counted as separate failed SSH login attempts because they may describe the same underlying authentication attempts.

**Finding:** Repeated SSH authentication failures are confirmed. The complete count requires a defined time window and deduplication of related log records.

### 2. Over what time period?

The supplied logs show two separate activity periods:

- **First period:** Approximately `11:55:58` to `11:56:15` UTC+05:30.
- **Second period:** Approximately `12:10:48` to `12:11:08` UTC+05:30.

The successful login occurred at `12:11:35.546310` UTC+05:30.

### 3. Which account was targeted?

The account `vm2` was targeted by the observed failed SSH authentication attempts and subsequently authenticated successfully.

### 4. Did authentication subsequently succeed?

Yes. The endpoint recorded:

`2026-10-17T12:11:35.546310+05:30 vm2 sshd-session[11159]: Accepted password for vm2 from 192.168.34.138 port 33084 ssh2`

This confirms a successful password-based SSH authentication from the same source IP.

It does not establish whether the login was authorized or whether the account was compromised.

### 5. Were there other suspicious events from the same source?

Yes. The logs show repeated authentication failures from `192.168.34.138`, followed by successful authentication.

At `12:12:09.442970`, a sudo session was opened for `vm2` to run `/usr/bin/tail -n 50 /var/log/auth.log`.

This command reads authentication logs. It is consistent with legitimate troubleshooting or investigation, but its context should be verified. The supplied record shows the session opening; it does not, by itself, prove that a malicious command was executed.

### 6. Was the source authorized to access the endpoint?

Unknown.

The source IP is within the lab's private network address space, but private addressing does not establish trust. Confirm the source VM's identity, the intended test activity, and whether the login at `12:11:35` was expected.

### 7. Is there evidence of successful compromise?

The logs confirm successful authentication. They do not independently prove unauthorized access, privilege escalation by an attacker, persistence, lateral movement, or data exfiltration.

Further investigation is required before classifying the event as a confirmed compromise.

## 8. Evidence and Findings

- **Supporting evidence:** Multiple `Failed password for vm2` entries in `/var/log/auth.log`.
- **Timestamp:** `11:56:00`–`11:56:10` and `12:10:51`–`12:11:07` on October 17, 2026.
- **Source:** `192.168.34.138`.
- **Interpretation:** The source repeatedly attempted password authentication against the `vm2` account.
- **Confidence:** High that repeated failures occurred; the intent behind them is not independently established.

### Finding 2 — Wazuh detected repeated authentication failures

- **Supporting evidence:** Wazuh alert for rule `100200`, level `10`.
- **Timestamp:** Event time `11:56:10.848578` UTC+05:30.
- **Source:** Wazuh Manager `vm1`.
- **Interpretation:** The configured detection produced a high-priority alert consistent with its intended purpose.
- **Confidence:** High that the alert exists; further testing is needed to validate all correlation conditions.

### Finding 3 — Successful SSH authentication after failures

- **Supporting evidence:** `Accepted password for vm2 from 192.168.34.138 port 33084 ssh2`.
- **Timestamp:** `12:11:35.546310` UTC+05:30.
- **Source:** `192.168.34.138`.
- **Interpretation:** The source successfully authenticated as `vm2` after repeated failures.
- **Confidence:** High that authentication succeeded; authorization and compromise remain undetermined.

### Finding 4 — Subsequent sudo session

- **Supporting evidence:** `sudo: pam_unix(sudo:session): session opened for user root(uid=0) by vm2(uid=1000)` and the associated command record.
- **Timestamp:** `12:12:09` UTC+05:30.

- **Interpretation:** The `vm2` account initiated a sudo session and requested access to authentication logs. The supplied command record identifies `tail -n 50 /var/log/auth.log`.
- **Confidence:** High that the sudo session was opened; the available evidence does not establish malicious intent.

## 10. MITRE ATT&CK Mapping

### T1110 — Brute Force

**Tactic:** Credential Access

The repeated failed SSH password attempts are consistent with brute-force behavior and support investigating this technique.

However, the logs do not establish whether the activity was an automated password-guessing attack, manual password-entry mistakes, or an authorized test.

The supplied evidence does not justify assigning a more specific brute-force sub-technique without additional information about the method used.

### T1078 — Valid Accounts

The successful login demonstrates authentication with valid credentials, but it does not prove those credentials were stolen or misused.

Map this technique only if further investigation establishes that the account was used in unauthorized activity.

## 12. Analyst Verdict

**Selected verdict: Suspicious activity — investigation required.**

### Reasoning

The repeated SSH authentication failures and subsequent successful login from the same source IP constitute a suspicious authentication sequence. Wazuh generated a Level 10 alert, and the endpoint logs confirm successful authentication followed by a sudo session.

However, the evidence does not establish that the source was unauthorized or that a compromise occurred. The activity could also be consistent with an authorized lab test or legitimate administrative troubleshooting.

The incident should remain open until the source system, successful login, and post-login activity have been validated.

## 13. Incident Response

### Containment

**Status: No containment action documented in the supplied evidence.**

Recommended actions:

1. Confirm whether `192.168.34.138` is an authorized lab system.
2. If the login is unauthorized or cannot be explained, restrict the source's access to the affected endpoint using an appropriate lab firewall rule.
3. If account compromise is suspected, revoke active sessions where feasible and reset the account's credentials from a trusted administrative session.
4. Preserve relevant SSH, authentication, sudo, and Wazuh logs before performing disruptive changes.

Do not block the source or disable the account solely on the assumption that the alert proves malicious activity.

### Eradication

No confirmed compromise or persistence mechanism has been identified.

If subsequent investigation confirms unauthorized access:

- Identify and remove unauthorized SSH keys or account modifications.
- Inspect for unauthorized services, scheduled tasks, cron entries, and other persistence mechanisms.
- Review installed software and modified configuration files.
- Rotate credentials that may have been exposed.

### Recovery

After any confirmed compromise has been addressed:

- Validate account security and SSH configuration.
- Verify that unauthorized persistence has been removed.
- Confirm Wazuh agent connectivity and telemetry collection.
- Monitor for repeated authentication failures or new suspicious logins.
- Document the recovery actions and closure rationale.

## 14. Detection Evaluation

### Did the rule trigger as expected?

Wazuh generated the expected custom alert for rule `100200`. Additional testing is required to establish its exact threshold and correlation behavior.

### Did it generate false positives?

No false-positive test results were supplied. A controlled benign test should be performed to evaluate whether legitimate failed logins trigger the rule too frequently.

### Did it miss any relevant events?

The supplied evidence does not include the complete set of Wazuh alerts for the second authentication-failure period or a confirmed alert for rule `100201`. Whether the second period triggered the expected alerts remains unknown.

### Is the threshold appropriate?

The current threshold is five matching events within 180 seconds. This is a reasonable lab starting point, but it should be evaluated against observed benign and malicious test activity.

### What improvements are needed?

1. Validate rule `100200` using `wazuh-logtest` and controlled authentication attempts.
2. Confirm that source IP correlation works as intended.
3. Verify whether the suppression interval affects subsequent alerts.
4. Test rule `100201` with a controlled successful login following a qualifying brute-force alert within its configured window.
5. Build an investigation query that correlates failures and successful authentication by source IP, account, host, and event time.
6. Investigate the difference between the event timestamp and Wazuh's indexed timestamp.
7. Add contextual enrichment where possible, such as source asset identity and whether the login was expected.

## 15. Lessons Learned

- Repeated SSH authentication failures should be investigated in context rather than treated as conclusive proof of an attack.
- A successful login from the same source after repeated failures raises the priority of the investigation.
- Correlation must account for time windows, source identity, and the difference between event time and ingestion time.
- Successful authentication does not establish authorization or prove compromise.
- Sudo activity after login should be correlated with the command, user, session, and surrounding events.
- Detection rules require both positive and negative testing.
- Good SOC reporting separates verified facts, hypotheses, and recommended actions.

## 16. Final Conclusion

The investigation confirmed repeated SSH authentication failures against `ubuntu_vm2` from `192.168.34.138`. Wazuh generated a Level 10 alert using custom rule `100200`.

The endpoint subsequently recorded a successful password-based SSH login for `vm2` from the same source at `12:11:35.546310` UTC+05:30, followed by a sudo session at `12:12:09`.

This sequence warrants further investigation, but the supplied evidence is insufficient to confirm unauthorized access or account compromise. The incident remains open pending validation of the source system, authorization of the successful login, and review of post-login activity.

The next priority is to determine whether the successful login was an expected lab action, verify the associated Wazuh detections, and preserve additional endpoint evidence before assigning a final incident verdict.
